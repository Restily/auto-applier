# ADR-0008: Encryption of user secrets at rest

- Status: accepted
- Date: 2026-09-27
- Deciders: architect

## Context
User secrets: Telegram MTProto sessions, Gmail OAuth refresh/access tokens, SMTP passwords, extension tokens. PRD: encrypted at rest, never returned to the browser, deleted on disconnect or account deletion; a leak means account takeover. Only the Python backend needs plaintext (to send).

## Options considered
1. **Application-level AES-256-GCM in the Python backend** with a keyring from the environment, ciphertext in a table that no API role can read.
2. Supabase Vault (`vault.secrets`, pgsodium-based): encryption keys managed inside the database; any DB superuser session can decrypt; pgsodium is being deprecated upstream.
3. pgcrypto with a key passed per query: the key travels in SQL and ends up in logs.

## Decision
- **AES-256-GCM** via `cryptography` (Apache-2.0/BSD) in `autoapplier/security/secrets.py`: `encrypt(plaintext: bytes, *, aad: bytes) -> EncryptedBlob` / `decrypt(blob, *, aad) -> bytes`; 96-bit random nonce per encryption; **AAD = `user_id|kind|connection_id`** so a ciphertext cannot be moved to another user or connection.
- **Keyring:** `APP_ENCRYPTION_KEYS="k2:<base64 32 bytes>,k1:<…>"` (first = active for encryption, all usable for decryption) → key rotation by re-encrypting in a job. Local dev keys are generated by `scripts/sync_env.py` into the git-ignored `backend/.env`; tests use a fixed test key.
- **Storage:** `private.user_secrets(id, user_id, connection_id, kind, key_id, nonce, ciphertext, created_at, rotated_at)` in schema **`private`**, which is **not exposed** through the Supabase Data API; RLS enabled with no policies; all privileges revoked from `anon`/`authenticated`. Rows cascade-delete with the connection and the user.
- **Extension tokens are not encrypted but hashed** (SHA-256 of a 256-bit random token, ADR-0005): the backend never needs them back.
- No API response schema contains a secret field; connection endpoints return status/metadata only. Logs redact secrets (structured logging with a denylist of keys), and pydantic `SecretStr` is used for secrets in settings/models.

## Consequences
- Positive: DB dumps and Data API access reveal nothing; key compromise requires the backend env; per-row binding via AAD.
- Negative: key management is ours (backup of `APP_ENCRYPTION_KEYS` is an owner's production task, recorded in the README at MR).
- Follow-ups: implemented with the first secret (M3, S-013); the MR security audit checks for secret leakage in responses and logs.

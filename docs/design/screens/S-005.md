# Screen spec S-005: Settings — interface language (English/Russian)

_Owner: Designer · 2026-09-27 · Design system: docs/design/design-system/autoapplier/MASTER.md_

Owns the Settings screen's overall layout (Account, Language, and the top of Your data / Danger zone). S-006 owns the detailed states/copy for the Your data and Danger zone cards shown here — this file gives their layout position and summary copy only, S-006 is authoritative for their behavior.

## Purpose and entry points

Let a signed-in user see and change their interface language, and give Settings a home for account-level actions. Covers the **global** language behavior too (detection on first visit, where the switcher lives, how the choice persists) since S-005 is the natural owner of "language" as a cross-cutting concern — MASTER §8.4 cross-references this file for the header switcher's detailed behavior. Entry points: account-menu "Settings" (MASTER §8.4) · sidebar "Settings" item (full shell, once it exists in the nav) · direct link from anywhere that mentions a setting (e.g. a future low-credit email).

## Global language behavior (applies everywhere, not just this screen)

- **First visit, no stored preference** (AC1): read the browser's language preference (`Accept-Language` / `navigator.language`). If it indicates Russian (`ru`, `ru-RU`, `ru-*`), the entire UI — including this being-viewed-for-the-first-time Sign up screen — renders in Russian. Any other value (including no match) renders in English. This check happens once, before first paint, not as a banner or prompt asking the user to confirm.
- **Explicit switch** (AC2): the header switcher (MASTER §8.4) and this screen's Language card are the same setting, changing one changes the other instantly — no separate "Save" step for language. Every page, every validation message, and every email template (password reset, future notifications) switches to the chosen language. For a signed-in user the choice is written to their profile (not just a cookie/`localStorage`), so it's identical on another device the next time they sign in there (AC2, "across devices"). For a signed-out visitor it's kept client-side (cookie or `localStorage`) until they sign up/in, at which point it becomes their stored preference (don't discard a deliberate pre-signup choice).
- **Never confused with cover-letter language**: the PRD also generates cover letters in the *vacancy's* language (M2+), which is unrelated to this UI-language setting and must not be the same toggle or the same stored field — noted here so it isn't accidentally conflated during implementation.
- **No missing-key fallback ever visible** (AC3): if a string is somehow untranslated, the system falls back to the English copy silently — the raw i18n key (e.g. `settings.language.title`) must never render as visible text. Every string in every screen spec's Copy table in this design system has both an EN and a RU value for exactly this reason; qa-automation's i18n check (AC3) is what verifies none were missed at build time.

## States

- **Default**: as drawn; current language pre-selected in the radio group, matching whatever the header shows.
- **Language switch in progress**: selecting the other radio option re-renders the page's strings immediately (client-side dictionary swap) while the profile-persistence write happens in the background; if that write fails (signed-in user, network hiccup), the UI stays in the newly-selected language (don't flip it back — jarring) and a toast explains the choice didn't save yet: "Language changed here, but we couldn't save it to your account — try again" / "Язык изменён здесь, но не удалось сохранить в аккаунте — попробуйте ещё раз."
- **Sign out**: same as MASTER §8.4 / S-001 §5 — immediate, no confirmation dialog.
- **Loading** (initial Settings fetch): `Skeleton` for the Account card's email line; Language card can render immediately (it only needs the already-known current locale, not a network round trip).

Language option labels are deliberately shown in their own language regardless of the current UI language ("English" always reads "English," "Русский" always reads "Русский," never translated to "Английский язык" / "English language") — a widely-understood convention (autonym labeling) that also means a user who landed in the wrong language by mistake can still find their way out.

## Validation messages

None — a `RadioGroup` with two mutually exclusive, always-valid options has nothing to validate. The only failure mode is the persistence-write failure above, which is a toast, not a field error.

## Responsive behavior (375 / 768 / 1280)

Single column at all three widths; Card order unchanged. At 375px the two radio options stay stacked vertically (never side-by-side — two short words don't need to force a horizontal layout, and vertical keeps a consistent tap-target height). Destructive "Delete account" button stays full-width on mobile like every other primary-ish action, but keeps its `destructive` coloring so it never reads as the page's main affirmative action.

## Accessibility

- Focus order: skip link → shell header/nav → Account card (email text is not focusable; reset-password link → Sign out button) → Language card (radio group, arrow-key navigation between the two options, standard `RadioGroup` pattern) → Your data card (Download button) → Danger zone card (Delete button).
- Language `RadioGroup` has a `fieldset`/`legend` = "Interface language" / "Язык интерфейса" so screen readers announce the group name, and each option's checked state is announced on arrow-key change.
- The Danger zone `Card` is not given any special ARIA "danger" role — its meaning is carried by the heading text, the body copy, and the button's `destructive` styling (border + `--danger` text/fill per MASTER), which is enough; inventing a non-standard role would only confuse assistive tech.
- Contrast: destructive button uses `--danger`/`--on-danger` (5.9:1, MASTER §2.1); radio group focus ring uses `--ring` at the standard 2px/2px-offset treatment.

## Interactions and motion

- Language switch: string swap is instant (this is content changing, not a transition to animate — animating text replacement across a whole page would be exactly the kind of decorative motion MASTER §3.7 rules out).
- Save-failed toast: `--duration-base` fade in/out, `Sonner` default timing.
- Everything else: standard component defaults (button hover/focus, no page-level animation on load).

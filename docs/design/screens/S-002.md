# Screen spec S-002: Sign in with Google

_Owner: Designer · 2026-09-27 · Design system: docs/design/design-system/autoapplier/MASTER.md_

Extends S-001 (Sign up / Sign in) — this spec covers only what Google adds: the button itself (already placed in S-001's layout), the round-trip to Google and back, and its three extra states. It does not duplicate S-001's field layout. Google sign-in is an **authentication method**, not a **channel connection** — it does not need the risk-consent pattern that email/Telegram/LinkedIn connections require later (M3/M4); it carries no sending capability, only identity.

## Purpose and entry points

Let a visitor sign up or sign in with one click using an existing Google account, skipping password creation entirely. Entry points: the "Continue with Google" button on both `/sign-up` and `/sign-in` (S-001 §Layout).

## Layout

No new screen geometry — reuses S-001's 440px auth card. Two additions:

```
On return from Google, before the app can render the real destination
(typically <2s — a backend token exchange, not a form):

┌──────────────────────────────────────────────────────────┐
│  AutoApplier                                           EN ▾│
├──────────────────────────────────────────────────────────┤
│                                                              │
│                        ⟳  Signing you in…                   │
│                                                              │
└──────────────────────────────────────────────────────────┘
   centered, same focus shell, no card — just an icon-less
   spinner + one line, since there is nothing to interact with
```

If Google OAuth is not configured in the environment (AC3): the button **and** the divider ("or continue with email") are both omitted — not disabled, not shown grayed out. The email form becomes the first thing in the card, right below the heading, with no reserved gap.

## Components

| Area | Component (UI kit) | Variant | Notes |
|---|---|---|---|
| Google button | `Button` | `outline`, full width, 20px Google "G" mark (brand mark only, not a Lucide icon — see Google's own brand asset) + label | Placed first in the card (S-001), above the divider |
| Callback interstitial | custom | — | Spinner (`Loader2`, animated per MASTER §3.7) + `--text-body` line, no card, no header credit-balance (session isn't confirmed yet) |
| Cancel message | `Alert` | `default` (neutral, not `danger` — the user chose to cancel, it isn't an error) | Rendered on the Sign in screen, above the fields |

## States

- **Available**: button renders as in S-001's layout; default/hover/focus-visible/active per MASTER Button spec.
- **Hidden** (AC3): Google not configured — button and divider both absent, see Layout. This is a build-time/env condition, not a runtime toggle a user can trigger.
- **In progress**: click → immediate full-page redirect to Google's consent screen (Google's own UI, outside our design system — nothing to spec). No spinner needed on our side for this leg since the browser's own navigation is the loading indicator.
- **Callback (returning from Google)**: interstitial above, then one of:
  - **New account** → created, granted the 20-credit sign-up bonus (once — AC1), redirect to the Onboarding checklist (S-001 §Onboarding checklist), same toast as email sign-up: "You've got 20 free credits."
  - **Existing account** (same verified email already registered) → signed in, no second bonus, redirect to that account's normal landing (Onboarding checklist if incomplete, else Profile).
  - **Cancelled on Google's screen** (AC2) → redirect to `/sign-in` (always sign-in, regardless of whether the user started from sign-up — AC says "they return to sign-in"), neutral `Alert` shown once: "Sign-in with Google was cancelled," no account created, email/password fields empty and ready.

## Copy

| Key | EN | RU |
|---|---|---|
| Google button | Continue with Google | Продолжить через Google |
| Callback interstitial | Signing you in… | Выполняется вход… |

(Sign-up bonus toast reuses S-001's "You've got 20 free credits" / "Вам начислено 20 бесплатных кредитов" — same copy regardless of which method created the account, so the two paths never feel like different products.)

## Validation messages

None — Google's own consent screen handles its own errors/validation; our side only branches on success vs. cancel (§States). If the backend token exchange itself fails (network error, Google outage — not a user cancel), treat it as the generic load-error pattern (MASTER §7 "Error, section/page failed to load"): icon, "Something went wrong," "Try again" button that re-starts the Google flow from `/sign-in`.

## Responsive behavior (375 / 768 / 1280)

Identical to S-001 at every width — the button is one more full-width element in the same card, the callback interstitial is a single centered line at any viewport. No layout deviates by breakpoint beyond what S-001 already specifies.

## Accessibility

- Google button sits first in the card's focus order (S-001 §Accessibility, step 3), has a real accessible name "Continue with Google" (not just the brand mark), and meets the same 44px minimum height as every other control in the card.
- The callback interstitial's status text is in an `aria-live="polite"` region so screen-reader users get "Signing you in…" announced without anything stealing focus.
- On return, focus moves programmatically to the destination page's `h1` (Onboarding checklist heading) on success, or to the cancel `Alert` (`role="alert"`, `tabindex="-1"` + `.focus()`) on cancellation — same pattern as S-001's form-level errors, so a keyboard/screen-reader user is never left with focus lost at the top of the document.
- Contrast: the outline button's border and text follow MASTER's standard `Button` `outline` variant (`--input-border` / `--foreground`, both already ≥3:1 / ≥4.5:1); the neutral cancel `Alert` uses `--foreground` text on `--surface-sunken`, not the danger palette, since nothing went wrong.

## Interactions and motion

- Click → immediate browser navigation to Google (no local transition to animate).
- Callback interstitial: appears instantly on return (no fade-in delay — this is already a wait the user is experiencing), spinner uses the standard `Loader2` rotation, disabled entirely under `prefers-reduced-motion` in favor of the static text alone ("Signing you in…" with no spinning glyph).
- Cancel `Alert`: `--duration-base` fade in, same as any other form-level alert (S-001).

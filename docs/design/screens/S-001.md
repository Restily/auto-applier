# Screen spec S-001: Sign up, sign in, sign out, password reset

_Owner: Designer · 2026-09-27 · Design system: docs/design/design-system/autoapplier/MASTER.md_

Covers four screens (Sign up, Sign in, Forgot password, Reset password) that share one layout, plus sign-out and the Onboarding checklist landing they redirect to (own section near the end of this file). S-002 (Google sign-in) extends the Sign up / Sign in screens defined here — see S-002 for the Google-specific button/consent states, this file is the base layout it attaches to. S-004 extends the Onboarding checklist's "Complete your profile" step (its "what's missing" sub-copy) defined below.

## Purpose and entry points

Let a visitor create an account or an existing user sign back in, with a low-friction path (email+password, no email verification gate — the account works immediately) and a working self-serve password reset. First-touch entry point for every user; also where a session that expired mid-visit sends people back.

Entry points: marketing/none (out of scope — this is app-first, no landing page in MVP) → `/sign-up` (default first visit) · `/sign-in` (returning user, or link from Sign up) · `/sign-in/forgot-password` (link from Sign in) · a one-time emailed link → `/reset-password?token=…` · any protected route when signed out → redirects to `/sign-in?next=<path>`.

## States

### 1. Sign up (`/sign-up`)
- **Default**: empty form, submit disabled until email + password both have content (still client-validated on submit, not just on blur, so a screen-reader user tabbing straight to submit gets a real error).
- **Loading** (submit in flight): button shows spinner only (`aria-label="Signing up…"` / `"Регистрируем…"`), fields disabled, button stays its resolved width.
- **Field errors**: malformed email / password <8 chars — inline, see Validation.
- **Duplicate email**: form-level `Alert` (danger) — see Copy — nothing is created, form stays filled in except password (cleared for safety). The alert is a plain-text message on its own line, then a separate actions row of two link-style buttons ("Sign in" / "Reset password") below it — **not** inline bold/links embedded mid-sentence: an earlier draft tried that and the prototype (`docs/design/prototypes/S-001.html`) showed it reflowing into choppy, hard-to-scan fragments at 375px (multiple short bold runs wrapping independently). A message line + a button row wraps as whole units instead and stays legible at any width.
- **Success, bonus granted** (`signupBonusGranted: true` — the normal case): redirect to the Onboarding checklist (§Onboarding checklist, below), toast "You've got 20 free credits," header balance badge shows `20`.
- **Success, bonus not granted** (D5 — `signupBonusGranted: false`, a re-sign-up on an email that was used on a now-deleted account): same redirect, **no toast at all** — not a substitute "0 credits" toast, not an explanation, nothing. The header balance badge just shows `0`, styled exactly like any other balance (same weight/color as `20` or `7` — see Header note below): a plain fact, not a flagged or muted-down state (the balance badge has exactly one visual treatment, MASTER §8.2 — no "low/zero" variant), and nothing on this screen implies the user did anything wrong or is being treated differently. The account is fully usable at 0 credits (it can still browse/set up a profile; spending credits is a later milestone's concern). If the product ever needs to say something at this balance, it belongs on the credits/billing surface (out of scope for M1), never as an unexplained toast at sign-up.

### 2. Sign in (`/sign-in`)
- **Default**: empty form.
- **Loading**: same pattern as sign up.
- **Invalid credentials**: form-level `Alert` (danger) "Invalid email or password" — identical wording whether the email is unknown or the password is wrong (AC4; prevents account enumeration). Both fields get the `--danger` border treatment together, not individually.
- **Success**: redirect to `next` param if present and same-origin, else to the post-onboarding landing (Onboarding checklist if incomplete, else Profile).

### 3. Forgot password (`/sign-in/forgot-password`)
- **Default**: single email field + submit.
- **Loading**: same pattern.
- **Success**: form is replaced in place by a confirmation panel (icon `MailCheck`, `--text-h3`, one line) — intentionally neutral about whether the address has an account (§Copy), matching sign-in's non-enumeration stance. No error state for "email not found" for the same reason.

### 4. Reset password (`/reset-password?token=…`)
- **Token valid**: new-password field (+ reveal toggle, + the same 8-char requirement line) + submit.
- **Loading**: same pattern.
- **Token expired or already used**: the form never renders; instead an error panel (icon `AlertTriangle`, `--text-h3` "This link has expired," one line, button "Request a new link" → Forgot password). Checked once on page load, not after a failed submit, so the user isn't asked to type a password first.
- **Success**: toast "Password updated. Sign in with your new password," redirect to Sign in with the email field pre-filled if known client-side.

### 5. Sign out (account menu action, not its own page)
Immediate on click — no confirmation dialog (it's a reversible, low-cost action). Clears the session, redirects to Sign in. Any other open tab on a protected page redirects to Sign in the next time it makes a request (session cookie/token gone).

### 6. Protected route while signed out
Redirect to `/sign-in?next=<path>`, no error toast (routine, not a failure). Exception: if a previously-valid session just expired (not "never signed in"), show a toast on arrival at Sign in: "You've been signed out. Sign in again."

| Field / condition | EN | RU | Trigger |

All inline errors: `--danger` border on the field, `--danger` text below (replaces helper text), small `AlertCircle` prefix icon, `role="alert"`, fades/slides in over `--duration-fast` (not an instant snap — the UX checklist flags 0ms state changes as an anti-pattern).

## Responsive behavior (375 / 768 / 1280)

- **1280 / 768**: centered 440px card as drawn above; header full width with logo left, language switcher right.
- **375**: card loses border/shadow, becomes the page (§Layout); 16px side gutter; all fields and the submit button are full width; Google button and email/password stack in the same order as desktop, nothing reflows to columns (this form was never multi-column). Header compresses to icon-only logo mark + language switcher (no wordmark) to keep 44px tap targets comfortable in 60px.
- Submit button and inputs keep a 44px+ height at every width (touch target minimum), independent of the 15px `--text-ui` type size.

## Accessibility

**Focus order (sign up, representative — sign in/reset follow the same left-to-right, top-to-bottom pattern minus the fields they don't have):**
1. Skip link (visually hidden until focused)
2. Header: logo (not a link pre-auth, or link to `/` if that resolves to sign-up — no-op is fine, don't force a focusable non-action) → language switcher
3. Card: Google button
4. Email input
5. Password input → reveal-toggle button (part of the same field, tab stop immediately after)
6. Submit button
7. Footer link ("Sign in" / "Sign up")

- Every input has a real `<label>` (not a placeholder standing in for one); placeholder, if any, is example text only and never the only accessible name.
- The password requirement line is linked via `aria-describedby` on the password input, not just visually nearby, so it's read when the field receives focus.
- Form-level errors (`Alert`, `role="alert"`) are placed immediately before the fields they relate to and receive programmatic focus on submit failure (`tabindex="-1"` + `.focus()`) so keyboard/screen-reader users land on the error instead of a silently-unchanged form.
- Contrast: card on background and all text/button pairs per MASTER §2.1 (body text 18.0:1, primary button text 5.8:1) — nothing here introduces a new color. The duplicate-email/invalid-credentials `Alert` sits on `--danger-subtle`; its message text is `--foreground` (15.2:1 on that tint), not the raw `--danger` red (MASTER §2.4 — raw semantic-on-own-subtle isn't reliably 4.5:1; `--success` on `--success-subtle` actually fails at 4.49:1, which is why this isn't a per-screen judgment call).
- `lang` attribute on `<html>` matches the active UI language, set before the form renders (not after a flash of the other language).

## Interactions and motion

- Field validation errors: `--duration-fast` fade + 4px slide-in, per MASTER §3.7 (state changes are never literally instant).
- Form-level `Alert` on invalid-credentials/duplicate-email: `--duration-base` fade in above the fields.
- Forgot-password success and reset-password success: the form is replaced in place (not a route change) with `--duration-base` cross-fade, so focus can move predictably to the confirmation heading.
- Submit button loading spinner: appears immediately (no fade delay — delaying loading feedback itself reads as lag, per the Touch & Interaction priority in MASTER).
- Respect `prefers-reduced-motion`: all of the above become instant state swaps, no transform/opacity animation.

## Onboarding checklist (landing screen after sign-up)

A self-contained fifth screen, specified here because S-001's own acceptance criteria make it the sign-up destination. S-004 extends its "Complete your profile" step with the exact missing-fields sub-copy.

### Purpose and entry points

One hub that names what's left before the account is fully usable, so a new user never has to guess what to do next. Built to hold multiple steps (more arrive in M2+: connect a channel, create a search) even though **M1 ships exactly one step** ("Complete your profile") — a single-item checklist is intentional, not a gap: it's the same component the later milestones populate, not a placeholder to be redesigned. Entry points: automatic redirect right after sign-up/sign-in-with-Google (S-001/S-002); reachable again any time from the account menu until every step is complete.

### Validation messages

None on this screen — it only links out to screens that validate.

### Responsive behavior (375 / 768 / 1280)

Single column at every width (this was never a multi-column page). Card padding and page gutter follow MASTER §3.4 (32/24/16px). Progress text and step body never truncate — both are short fixed strings, verified to fit at 375px in both languages.

### Accessibility

- Focus order: skip link → header (logo, credit balance, language, account menu) → progress text (not focusable, but the `Progress` element has `aria-valuenow`/`aria-valuemax`) → step card's action button → (once present) all-done CTA.
- The progress bar's accessible name states the same thing as the visible text ("0 of 1 steps complete" / "Выполнено шагов: 0 из 1"), so it isn't announced as a bare percentage.
- Step completion is conveyed by icon + "Done" text + background change together, never by color/icon alone.
- Contrast: complete-state text/icon on `--surface-sunken` follows the same `--success` (5.1:1) / `--foreground` pairs verified in MASTER §2.1.

### Interactions and motion

- Step flipping from incomplete → complete (e.g. returning from a completed Profile Editor save): `--duration-base` cross-fade of the card's icon/background/action together, plus the progress bar animates to its new value over `--duration-base`. This is the one place a small celebratory-adjacent motion is earned (MASTER §3.7's "one orchestrated moment") — it stays understated: no confetti, no bounce, just a calm state change.
- All-done block: enters with the same `--duration-base` fade once triggered, doesn't push the step card layout around abruptly (the step card's own height doesn't change between its two states).
- `prefers-reduced-motion`: both become instant.

# Screen spec S-004: Fill and edit the profile manually

_Owner: Designer · 2026-09-27 · Design system: docs/design/design-system/autoapplier/MASTER.md_

Extends the Profile Editor defined in S-003 §Layout (3d) — same screen, same sections, same components. This spec adds: the no-resume entry point, the **Application answers** section, the required-field set and its validation, save/reload persistence, and the Onboarding checklist's missing-fields sub-copy (S-001 §Onboarding checklist). Read S-003 first for the shared layout; this file doesn't repeat it.

## Purpose and entry points

Let a user reach a usable, matchable profile without ever uploading a file — same destination screen as the resume path, just starting blank. Entry points: "Fill in manually instead" link on S-003's upload step (§3a) · "Fill in manually" action on S-003's extraction-failed panel (§3c) · re-opening the Profile Editor later to edit anything, resume-derived or not (the editor makes no distinction between fields that came from AI extraction and fields the user typed — once saved, they're all just "the profile").

## Layout

No new screen — this is S-003 §3d (Profile Editor) with every field starting empty instead of pre-filled, plus one additional section:

```
  │ ┌ Application answers ────────────────────────────┐          │ Card, below Languages
  │ │ Work authorization   [ Select…            ▾ ]     │          │
  │ │ Relocation readiness [ Select…            ▾ ]     │          │
  │ │ Notice period         [ Select…            ▾ ]     │          │
  │ │ Expected salary   [ Min ] – [ Max ]  [USD▾] [/mo▾] │          │
  │ └─────────────────────────────────────────────────┘          │
```

"Phone" (listed among S-004's application-answer fields in the story AC) lives in the **Contact info** section defined in S-003 §3d — it is one field, not duplicated here; this section covers only the fields that don't already exist elsewhere (work authorization, relocation readiness, notice period, expected salary).

No entry in this section is required to mark the profile "complete" (§States) — only the fields listed under Required below gate completion. These fields exist because they measurably change match quality and are asked once here rather than repeatedly per application.

## Components

Same as S-003 §Components, plus:

| Area | Component (UI kit) | Variant | Notes |
|---|---|---|---|
| Work authorization | `Select` | — | Options: "Authorized to work here without sponsorship" / "Would need visa sponsorship" / "Other" (reveals a short free-text `Input`) |

## States

**Manual start (no resume)**: every field in every section (S-003 §3d) renders empty. Required fields (§below) show their `*` and `aria-required` from the very first render — a first-time visitor should never discover a required field only after failing to save.

**Editing an existing (saved) profile**: fields pre-filled with the last saved values regardless of whether they originated from extraction or manual entry — there is no visual distinction between "AI-filled" and "typed" once saved (only the still-unsaved "We filled this from resume.pdf" banner, S-003, distinguishes a fresh extraction that hasn't been reviewed yet).

**Dirty / unsaved**: as soon as any field changes, the Save changes button becomes the emphasized (`default`) treatment if it wasn't already, and the "Unsaved changes" text appears beside it. Attempting to navigate away (route change or tab close) with unsaved changes triggers the browser's native "leave site?" prompt (`beforeunload`) — nothing is ever silently lost.

**Save behavior (D1): blocking is about format, not completeness.** The five required fields (Full name, Contact email, at least one Target title, at least one Skill, Years of experience) never block the write by being empty — only a *format* problem does. This produces three save states:

**Save blocked — format error** (AC2, format half): Contact email is malformed, a LinkedIn/Portfolio URL is malformed, or Expected salary Max < Min. Every invalid field gets the inline error treatment (S-003-style `--danger` border + message, `role="alert"`) simultaneously (not one at a time), the page scrolls to and focuses the first one, and the profile is **not** written — it stays exactly as it was before the attempt. No toast fires; nothing was saved, so there's nothing to confirm.

**Save succeeds, profile still incomplete** (AC2 completeness half + AC4): one or more of the five required fields is still empty/unset, with no format error present anywhere on the form. The write **does** happen (`is_complete` stays false). Every missing required field gets the same inline treatment as a blocked save (its own message from §Validation messages, `--danger` border, `role="alert"`, all simultaneously) and focus moves to the first one in fixed order (Full name → Contact email → Target titles → Skills → Years of experience) — visually almost identical to a blocked save, except a `Sonner` toast (`profile.savedIncomplete`, §Copy, `info` variant) confirms the write actually happened. The Onboarding checklist's "Complete your profile" step stays open, its body replaced by the `onboarding.missing` sub-copy (§below) next time it's viewed.

**Save succeeds, profile complete**: all five required fields present and no format error anywhere. `Sonner` toast "Saved" (MASTER §6.2, `success` variant), Onboarding checklist's "Complete your profile" step flips to done next time it's viewed (or immediately, if reached via the checklist's back-navigation — see S-001 §Onboarding checklist Interactions).

**Reload after save** (AC3): re-fetches the saved profile; every field, including Application answers, shows exactly what was last saved — this is a statement about the API contract as much as the UI, called out here because it's directly tested by the AC: the editor must never rely on client-only state (no field is "saved" only in a Redux/local store) — Save changes is a real write, and the initial load of this screen is a real read, every time.

**Missing (Onboarding checklist sub-copy, AC4)**: driven by the same missing-fields set as the save notice above. When the profile does not yet satisfy the required-field set, the checklist's "Complete your profile" step body (S-001 §Onboarding checklist) is replaced with `onboarding.missing` (§Copy) — the literal list of what's absent, sourced from the same five required fields, comma-joined (`Intl.ListFormat`), e.g.:
- All five missing (never started): default copy stays ("Upload a resume or fill it in…") — nothing to enumerate yet.
- Partially filled: "Missing: contact email, at least one skill" / "Не хватает: email для связи, минимум один навык" — comma-separated, in the fixed order Full name → Contact email → Target title → Skills → Years of experience, only the actually-missing ones listed.

## Validation messages

| Field | Condition | EN | RU |
|---|---|---|---|
| Full name | Empty | This field is required | Обязательное поле |
| Contact email | Empty | This field is required | Обязательное поле |
| Contact email | Malformed | Enter a valid email address | Введите корректный email |
| Target titles | Zero selected | Add at least one target title | Добавьте хотя бы одну желаемую должность |
| Skills | Zero selected | Add at least one skill | Добавьте хотя бы один навык |
| Years of experience | Not selected | This field is required | Обязательное поле |
| LinkedIn / Portfolio links | Malformed URL | Enter a valid URL | Введите корректную ссылку |
| Expected salary Max | Max set and less than Min | Max should be greater than min | Максимум должен быть больше минимума |

**Per D1, blocking is about format, not completeness, and applies the same way whether the field is required or optional:** a malformed Contact email, a malformed LinkedIn/Portfolio URL, or Expected salary Max < Min all block the write (you can't save garbage) — these are the *only* save-blocking conditions (§States "Save blocked — format error"). Leaving a required field empty (Full name, Contact email, Target titles, Skills, Years of experience) does **not** block the write: it saves with `is_complete: false`, the field highlighted, and the `profile.savedIncomplete` notice (§States "Save succeeds, profile still incomplete"). Leaving Links or Expected salary empty entirely — they're optional — blocks nothing either.

## Responsive behavior (375 / 768 / 1280)

Same single-column behavior as S-003 at every width. The Application-answers section's inline salary controls (Min – Max, Currency, Period) wrap to two rows at 375px — Min/Max stay paired on one row (they read as a unit), Currency and Period drop to the row below, each still ≥44px tall and full-width-ish (auto width with min-width, not squeezed to fit four controls on one 343px-wide row).

## Accessibility

Same focus order as S-003 §Accessibility, extended through the new section in visual order (Work authorization → Relocation readiness → Notice period → Expected salary's four controls left to right) before reaching Save changes.

- The four Expected-salary controls are grouped under one `fieldset`/`legend` ("Expected salary" / "Ожидаемая зарплата") so a screen reader announces the group, not four unrelated controls.
- On any save with an invalid field — whether it blocks the write (format error) or doesn't (a missing required field, D1) — focus moves to the first invalid field (in the fixed order from §States) and a page-level summary is **not** shown in addition: each invalid field's error is announced via its own `role="alert"` region, consistent with MASTER §7's "inline alone for 1 error" rule; if multiple fields are invalid at once, each still gets its own inline `role="alert"`, and focus moves to only the first one so keyboard users don't have to hunt.
- The `profile.savedIncomplete` toast (`Sonner`, MASTER §5) is announced through its own `aria-live="polite"` region and never takes focus — focus stays on the field the point above already moved it to. Because `role="alert"` is implicitly assertive and the toast's region is polite, a screen reader finishes the focused field's error first and the toast after, never both at once.
- "Unsaved changes" text is in a live region only when it *appears* (`aria-live="polite"`, announced once), not re-announced on every keystroke.

## Interactions and motion

- Field becomes dirty → Save button + "Unsaved changes" text fade in together over `--duration-fast`.
- Blocked save (format error): the same `--duration-fast` error fade used throughout (S-001/S-003), applied to every invalid field simultaneously, then focus + scroll to the first one (`scroll-margin-top` accounting for the sticky header). No toast — nothing was written.
- Save succeeds, still incomplete (D1): the same error fade + focus/scroll to the first missing required field, running together with the `profile.savedIncomplete` toast sliding in (`--duration-base`, MASTER §3/§5) — both start on the same tick, not queued one after the other.
- Save succeeds, complete: toast "Saved" per S-003; if reached from the Onboarding checklist, returning to it triggers that screen's incomplete→complete cross-fade (S-001 §Onboarding checklist Interactions).
- `prefers-reduced-motion`: all instant, as elsewhere.
